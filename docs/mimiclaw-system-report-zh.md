# MimiClaw：在 4 美元微控制器上运行完整的 LLM Agent Loop

**技术报告** — v1.0，2026 年 7 月
约 8300 行 C（main/），ESP-IDF + FreeRTOS，ESP32-S3

---

## 摘要

LLM agent 运行时正在经历一场持续的"瘦身运动"：从 OpenClaw 的四十余万行 TypeScript，到 nanobot 的四千行 Python，再到 PicoClaw、ZeroClaw 等不足 10 MB 的 Go/Rust 实现。但这条瘦身曲线在一个地方集体止步——它们全部依赖 Linux：进程、完整文件系统、动态语言运行时、包管理。MimiClaw 把这条曲线推过了最后一级台阶：在没有操作系统、没有进程、只有 512 KB 片内 SRAM 的裸机（bare-metal）环境中，用约 8300 行 C 实现了一个完整的 agent 运行时——ReAct 工具循环、LLM 自管理的持久记忆、可扩展技能系统、多通道消息接入、定时与心跳自主行为、以及硬件操作的安全护栏——运行在一颗数美元的 ESP32-S3 上，推理由云端 LLM API 承担。本报告论证这一工作的核心命题：**agent 运行时的本质不依赖操作系统**。我们逐项展示 Linux 上的 agent 原语如何被重建于嵌入式原语之上——进程变为 FreeRTOS 任务、异步框架变为消息队列、插件系统变为 Markdown 数据文件、向量记忆库变为模型自己读写的文本文件——并给出这一重建的完整资源账本、贯穿设计的四条工程原则，以及它暴露出的真正开放问题。

## 1. 引言：为什么把 agent loop 放进单片机

一个 LLM agent 运行时到底需要什么？剥去所有框架之后，答案是五件事：一个把"推理—调工具—看结果"循环起来的 loop；一组工具及其执行环境；跨会话的持久记忆；与外界的消息通道；以及无人触发时的自主行为。2025 年以来的 agent 运行时演化史，本质上是不断验证"上一层依赖其实是偶然的、不是本质的"：nanobot 证明了不需要四十万行框架，PicoClaw 和 ZeroClaw 证明了不需要 Python。但它们停在了 Linux 上，留下最后一个未被检验的假设：**agent 运行时需要一个操作系统吗？**

MimiClaw 的回答是否定的，并且是构造性的否定：它不是论证，而是一个在真实硬件上长期运行的系统。设备端保有全部的状态、编排逻辑与安全边界；云端模型是一个无状态的推理 oracle，每次调用之间对设备一无所知。这一分工——**智能在云端，架构在设备**——恰好把问题变得锋利：既然智能不占本地资源，那么 agent 的"架构部分"的最小充分实现到底有多大、需要克服什么？本报告的其余部分就是这个问题的实测答案。

这一形态并非玩具。设备直连 Telegram 与飞书、常驻在线、可 OTA 升级、断电重启后记忆完好；2026 年出现的同类系统（乐鑫官方的 ESP-Claw、WireClaw、zclaw）与 MimiClaw 相互印证：MCU 托管的 agent loop 已经是一个真实的系统类别，而 MimiClaw 属于开创这一类别的最早一批实现。

## 2. 裸机环境的五重约束

把 agent loop 从 Linux 移到裸机，要跨过的不是一道坎而是五道。逐一具体化：

**没有进程与调度器抽象。** nanobot 式运行时依赖异步框架（asyncio）管理并发：轮询消息、执行工具、调用 API 互不阻塞。裸机上只有 FreeRTOS 的静态任务与队列，且每个任务的栈在创建时一次性划定、不可增长——栈给小了溢出崩溃，给大了浪费寸土寸金的片内 SRAM。

**严苛且分层的内存。** ESP32-S3 只有 512 KB 片内 SRAM，其中相当部分被 WiFi 协议栈与 TLS 会话占据；外挂 PSRAM 提供 8 MB，但访问更慢且部分外设 DMA 不可用。一次 LLM 调用的请求体（系统提示 + 20 条历史 + 工具 schema）加响应缓冲就要几十 KB——放错位置，系统就没有内存可以工作。

**没有真正的文件系统。** SPIFFS 是平面结构：没有目录，只有带路径样式名字的文件；文件名长度有限（本项目曾为长会话文件名把 `SPIFFS_OBJ_NAME_LEN` 提到 64 才解决截断问题）。而 agent 的记忆范式（OpenClaw 的 MEMORY.md / 每日笔记 / 技能目录）恰恰是围绕目录树设计的。

**没有动态语言运行时。** Linux 上的 agent 用 Python/JS 热加载插件来扩展能力。裸机上代码就是固件，改一行要重新编译烧录——如果"扩展 agent 能力"必须走这条路，系统就死了。

**故障是常态而非异常。** 掉电、WiFi 中断、看门狗复位、NVS 损坏随时发生，且现场没有运维人员。一个常驻 agent 必须假设自己会在任意时刻被硬复位，并在没有人类干预的情况下恢复。

## 3. 系统设计

### 3.1 架构：消息总线与双核划分

系统的骨架是两条 FreeRTOS 队列构成的消息总线（inbound/outbound，深度各 16）。所有通道——Telegram 长轮询、飞书 webhook/轮询、WebSocket 网关、cron、heartbeat——只做一件事：把消息推入 inbound。agent loop 从 inbound 取消息、执行 ReAct 循环、把结果推入 outbound；一个独立的分发任务从 outbound 取出并路由回正确的通道。通道与 agent 之间完全解耦：增加一个新通道不触碰 agent 代码，agent 阻塞在 LLM 调用上时通道照常收发。

这一总线架构叠加在物理的双核划分上：**agent loop 独占 core 1（优先级 6），全部 I/O——三个通道任务、出站分发、串口 CLI——挤在 core 0**。效果是推理路径与 I/O 路径在硬件层面互不抢占：Telegram 轮询的 TLS 解密不会打断工具执行，agent 的 JSON 组装也不会让消息接收掉包。这是把 asyncio 的并发语义翻译成嵌入式原语的完整方案：异步框架变成队列 + 双核静态布局，回调变成阻塞式任务各守一摊。

消息内容以指针传递、所有权随消息转移（推入即让渡、失败方负责释放），队列满时显式丢弃并记日志——背压策略是"宁丢一条状态消息，不阻塞 agent"。

### 3.2 内存：分层策略与降级启动

内存管理浓缩为一条纪律：**大而冷的进 PSRAM，小而热的留 SRAM**。agent 的三块工作缓冲——16 KB 系统提示、32 KB 历史/流缓冲、8 KB 工具输出——全部 `heap_caps_calloc(MALLOC_CAP_SPIRAM)` 从 PSRAM 分配且一次分配终身复用（不在循环内反复 malloc，杜绝碎片化）；任务栈、TLS 会话、WiFi 缓冲留在片内 SRAM。所有缓冲定长、所有写入带边界检查——系统的内存占用在编译期就可以画出上界。

一个体现裸机生存哲学的细节是 agent 任务的**降级启动**：创建任务时按 24→20→16→14→12 KB 的阶梯依次尝试栈大小，哪一档成功用哪一档，每次失败都记录当时的内部堆余量。在一个内存状况随固件版本、连接数、TLS 状态浮动的环境里，这比"要么满配要么崩溃"多出一整段可用区间——**优雅降级优先于精确预算**。

### 3.3 记忆与上下文：把文件范式装进平面闪存

MimiClaw 的记忆系统没有向量数据库、没有嵌入模型，是 OpenClaw 文件范式的完整移植：`SOUL.md`（人格）、`USER.md`（用户画像）、`MEMORY.md`（长期记忆）、`daily/<日期>.md`（每日笔记）、`sessions/`（会话历史），全部是 SPIFFS 上的纯文本。关键的设计决定是：**记忆的写入者是模型自己**。固件只提供文件读写工具和系统提示中的记忆纪律（"学到用户的新信息立即写入 MEMORY.md""写前先读、用编辑而非覆盖""保持简洁、总结而非堆砌"），何时记、记什么、怎么组织，完全由 LLM 在对话中自主决定。设备由此获得了跨断电、跨复位的连续人格——而实现它的固件代码只有一百来行。

上下文组装是一套**定长预算制**：系统提示总预算 16 KB，其中长期记忆封顶 4 KB、近三天笔记封顶 4 KB、技能摘要封顶 2 KB，会话历史封顶 20 条——每一层各有硬上界，加起来仍在一次 API 调用的合理体积内。两个配套的瘦身机制值得单列：

- **会话瘦身**：持久化的会话只保留用户文本与最终回复，ReAct 中间过程（工具调用与结果）用完即弃。多轮工具调用产生的大量中间 token 不会累积进下一轮的上下文——这是在协议层面对"上下文随任务长度膨胀"问题的第一道闸门。
- **技能的渐进披露**：技能是 SPIFFS 上的 Markdown 文件，系统提示里只注入一份两 KB 的摘要清单；模型判断任务匹配某技能时，自己调 `read_file` 加载全文。扩展 agent 能力于是变成**写一个文本文件**——不重编译、不重烧录，甚至可以由 agent 在对话中给自己写新技能。这同时回答了"没有动态语言运行时怎么扩展行为"：把行为编码为数据，让解释器是云端的 LLM 本身。

### 3.4 工具与确定性护栏：固件不信任模型

工具层的设计前提是模型会出错，而纠错不能靠再问一次模型。两个机制体现这一哲学：

**策略白名单**（`gpio_policy`）：GPIO 操作在执行前经过固件内的静态白名单校验，模型无论生成什么参数都无法触碰白名单之外的引脚。安全边界由 C 代码定义，提示词只是礼貌性提醒。

**参数修补**：实践中发现模型调用 `cron_add` 时会漏填或错填投递通道与 chat_id（比如把字面量 "cron" 当作 Telegram chat_id）。固件的对策不是重试，而是**确定性地修补工具入参**——用当前消息的真实通道上下文直接覆写缺失或非法的字段，然后照常执行。这是一个值得推广的模式：**在模型输出与副作用之间，凡是固件确定知道正确答案的字段，由固件说了算。**

### 3.5 自主性与故障恢复

cron 服务（SPIFFS 上的 `cron.json`，至多 16 个任务，60 秒粒度）与 heartbeat（每 30 分钟读 `HEARTBEAT.md` 唤醒一轮 agent）让设备在无人消息时也有自己的"生活"：定时汇报、自检、模型给自己安排的后续任务——cron 任务本身就是模型通过工具创建的，即 agent 拥有安排自己未来行为的能力。

故障恢复贯穿每一层：NVS 检测到损坏即擦除重建；SPIFFS 挂载失败即格式化重来；WiFi 反复连不上则自动降级为强制门户（captive portal）配网热点；出站队列满则丢弃并记日志而非阻塞。所有持久状态（记忆、会话、cron、配置）都在闪存上，看门狗复位或掉电之后，设备带着完整记忆回到岗位。配合双 OTA 分区与串口 CLI，这是一台可以寄给非技术用户、坏了自己爬起来的设备。

## 4. 资源账本

**Flash（16 MB）**：2 × 2 MB OTA 应用分区 + 12 MB SPIFFS（记忆/会话/技能/配置）。固件本体约 2 MB——一个完整 agent 运行时占用的代码空间与一个中等 npm 依赖相当。

**RAM**：静态任务栈合计约 56 KB 片内 SRAM（agent 24 KB + 三通道与分发各 12 KB + CLI 4 KB）；agent 工作缓冲 56 KB 全在 PSRAM（16 + 32 + 8 KB）。粗略地说：**agent 的"架构部分"用不到 60 KB 片内内存就能运转**，其余留给协议栈与 TLS。

**上下文预算**：系统提示 ≤ 16 KB（内含记忆 4 KB + 笔记 4 KB + 技能摘要 2 KB 的分项上界），历史 ≤ 20 条，工具输出单次 ≤ 8 KB。

**代码量**：main/ 约 8300 行 C，214 次提交，多人协作的开源项目。作为参照：nanobot 约 4000 行 Python——但 Python 解释器本身在 MCU 上放不下；8300 行 C 是包含了全部通道、记忆、工具、配网、OTA 的完整数字，没有藏在运行时里的隐性依赖。

## 6. 如何评估这项工作

评估 MCU 托管的 agent 运行时没有现成的方法论。既有的 agent benchmark——AgentBench、ToolBench、WebArena、AndroidWorld——全部假设 loop 运行在主机上、工具是网页或 GUI 操作，没有一个能在设备端运行时上执行，更谈不上对其施加有意义的压力。因此我们沿三条轴线评估——系统成本、任务能力、可靠性——每条轴线有自己的指标、工作负载与对比对象。"没有合适的 benchmark"本身也是发现的一部分：下述任务集的设计目标就是作为未来 MCU-agent benchmark 的种子发布。

### 6.1 指标

| 类别 | 指标 |
|---|---|
| 系统占用 | flash 体积；SRAM 与 PSRAM 高水位（`heap_caps`）；上电到就绪时间；空闲功耗 |
| 每轮成本 | 端到端延迟及其分解（DNS / TLS 握手 / TTFB / token 流式接收 / 本地解析 / 工具执行）；上下行字节；输入/输出 token；每任务美元成本；每轮焦耳（INA226/PPK2） |
| 任务能力 | 对照程序化 ground truth 的成功率；每任务工具迭代次数；冗余调用率 |
| 记忆质量 | 跨会话召回准确率（探测 k 天前植入的事实）；硬复位后的召回；记忆文件增长速率 |
| 可靠性 | 7 天连续运行测试（崩溃次数、堆漂移、重连次数、消息丢失）；注入故障下的恢复率（WiFi 中断、看门狗复位、SPIFFS 损坏） |
| 安全性 | `gpio_policy` 处的危险动作拦截率；参数修补命中率（固件已有日志） |

所需的逐调用插桩（`llm_proxy` 中的计时与字节计数）与 SpecClaw 计划书中里程碑 M0 规定的基础设施完全相同，两项工作共享这套设施。

### 6.2 工作负载

两个互补的来源。其一，**可移植到主机的既有 function-calling 任务子集**（BFCL 风格的工具选择与参数填充问题，不需要 GUI），同一批任务、同一模型，在 MimiClaw 设备端跑一遍、在主机侧参考 loop 跑一遍：在模型能力恒定的条件下分离出运行时本身的开销与成功率代价。其二，**专门构建的 MCU 任务集**，五个类别——感知/执行（GPIO）、定时调度（cron）、跨会话记忆召回、多步编排、故障恢复——每个任务配程序化 ground-truth 判定，经 WebSocket 网关接入的主机侧模拟器加一个小型物理台架执行。前者锚定可比性，后者测量只有设备端运行时才能做的事。

### 6.3 Baseline 与对比对象

这里的"baseline"是五种不同的东西，各自回答不同的问题，方案会全部用到：(i) **同类运行时**（nanobot、OpenClaw），检验能力平价；(ii) **主机侧最小参考 loop**（同任务同模型），分离 MCU 平台本身的开销；(iii) **自身消融变体**（每次关掉一个机制），为每条设计主张定价；(iv) **对立架构**（loop 在主机、MCU 作为纯工具端点），检验 loop 放置的主张；(v) **已发表数字**（如 MEM1、StateAct 在 ALFWorld 上的结果），作为外部坐标锚点。下表列出外部对比对象；(iii) 类见 §6.4。

| Baseline | 同任务同模型 | 回答的问题 |
|---|---|---|
| 树莓派上的 nanobot（Zero 2 W 与 Pi 5） | 是 | 去掉操作系统付出什么、换来什么？预期：成功率持平，MimiClaw 在单价、空闲功耗、启动时间上占优，灵活性上落后 |
| 同类 MCU 系统：ESP-Claw、zclaw、WireClaw | 公共子集（对话、GPIO、定时任务） | MimiClaw 在自己所属类别中的位置？三者均无已发表的测量数据，这一对比本身即是贡献 |
| 云端编排架构（loop 在主机，MCU 作为 DCP/MCP 式工具端点） | 是 | loop 放在设备上值不值？关键差异点：断网存活、本地状态、线上字节量 |
| 固定运行时上的模型档位扫描（Haiku / Sonnet / Opus） | 是 | 这套运行时对模型能力的要求有多高——文件范式的记忆纪律在较弱模型下是否优雅退化？ |

### 6.4 消融

本报告的每个特色机制都对应一个开关，把设计主张变成可测量的差值：会话瘦身 vs 持久化完整 transcript（上下文增长、每轮成本、成功率）；渐进披露 vs 全部技能注入提示词（提示词 token、技能任务成功率）；参数修补开/关（定时任务成功率）；记忆纪律提示词开/关（召回准确率、记忆文件增长）。三处细化使消融更锋利：参数修补不只对照"关掉"，还对照"关掉但允许模型重试一次"——证明确定性修补优于多付一次调用的模型自纠；双核划分对照"全部任务钉到单核"，测量 agent 推理期间通道延迟的抖动——把 §3.1 的架构主张变成数据；上下文预算做扫描（历史 5/10/20/40 条；记忆上限 2/4/8 KB），描出成功率-成本曲线并定位拐点，检验当前默认值是接近最优还是仅仅出于习惯。

另一族消融来自一个代码级发现：单个 turn 内部，loop 在每次工具迭代时都会重新上传不断增长的完整消息数组（每次调用都对全量数组深拷贝后重建请求体），因此轮内上行量随迭代次数呈平方增长。为此我们实现一个**上下文压缩阶梯**——L0：全量拼接（现状，即 baseline）；L1：每工具输出预算加头尾截断；L2：确定性迭代摘要（早于最近一轮的迭代保留 tool_use/tool_result 配对——这是 API 硬约束——但结果收缩为一行状态、中间 text 块丢弃）；L3：纯占位符掩蔽，即 observation masking baseline [Complexity Trap, arXiv:2508.21433] 的设备端复现——并在每一档测量每 turn 上传字节、token、延迟与成功率。这个阶梯同时就是 TinyReAct 研究方向的 L1/L2 层级，同一组固件开关既服务工程优化也服务研究消融。

每配置至少 10 次运行，报告 95% 置信区间；故障注入按固定时间表回放；测试框架、任务定义与原始日志随代码一并发布。

## 7. 四条设计原则（可迁移的经验）

回看全部设计，四条原则反复出现，它们共同构成"裸机 agent 运行时"这一物种的设计语法：

1. **行为即数据。** 凡是可能变化的行为（人格、记忆、技能、定时任务）一律编码为闪存上的文本文件，由云端模型解释执行；固件只实现不变的机制。这绕开了"没有动态运行时"的约束，也让 agent 获得了修改自身行为的能力。
2. **一切资源定预算。** 每块缓冲、每层上下文、每个队列都有编译期可见的硬上界。裸机上没有 swap 也没有 OOM killer，"上界未知"等于"必然崩溃"。
3. **固件不信任模型。** 安全边界（白名单）与已知事实（参数修补）由确定性代码兜底；提示词负责引导，C 代码负责保证。
4. **降级优先于完美。** 栈阶梯启动、配网门户回退、队列满丢弃、损坏即重建——每个子系统都回答过"这一步失败了然后呢"，答案从来不是"不会失败"。

## 8. 局限与下一步

诚实的边界同样重要。**其一**，设备目前对云端是逐步依赖的：ReAct 每步一次 API 调用，每次调用支付一笔与 token 无关的固定成本（radio 唤醒、TLS 握手、往返延迟），断网时 loop 存活但推理瘫痪——这是后续工作（守卫式投机执行，见 `specclaw-research-proposal-zh.md`）的直接动机，而本报告描述的总线、工具白名单与文件持久化恰好构成其全部前置设施。**其二**，本报告给出的是设计与静态账本；第 6 节的测量方案已经明确但尚未执行，完成这些实验正是从"系统报告"走向"系统论文"要做的工作。**其三**，会话瘦身与定长预算控制了上下文体积，但记忆文件本身的增长仍依赖模型自律，缺少固件层的强制压缩机制。

这三条局限有一个共同点：它们都是**只有先把系统建出来才会浮现的问题**。这正是 MimiClaw 作为研究平台的价值——它把"MCU 上的 agent"从一个假设变成了一组可以测量、可以改进、可以发表的具体问题。
